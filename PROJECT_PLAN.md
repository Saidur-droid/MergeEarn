# MergeEarn Product Plan

## Mission

Make it extremely easy to turn a real GitHub issue into paid, verified work.

## One-line pitch

**Turn GitHub issues into funded bounties. Contributors fix the issue, submit a pull request, and get paid after verified work is merged.**

## Users

### Maintainer
Wants bugs/features solved with minimum coordination overhead.

Main flow:
1. Connect GitHub
2. Choose repository
3. Choose issue
4. Click `Add bounty`
5. Review AI-generated task summary and acceptance criteria
6. Set reward
7. Fund with Nimiq Pay
8. Review contributor PR
9. Merge/approve
10. Release payment

### Contributor
Wants clear work, objective completion rules, and reliable payment.

Main flow:
1. Connect GitHub
2. Browse funded bounties
3. Open a bounty
4. See reward + acceptance criteria + repo context
5. Claim/start work
6. Submit or link PR
7. Wait for verification/review
8. Get paid

## Core product loop

**Issue -> Bounty -> Fund -> Fix -> PR -> Verify -> Merge -> Pay**

This loop is the product. Everything else must support it.

## Primary wow moment

A maintainer opens an existing GitHub issue, clicks **Add bounty**, and MergeEarn instantly converts the issue into a clear paid task with acceptance criteria and a funding action.

The judge/user should think:

> "I can turn a GitHub issue into paid work in seconds."

## UX principles

### 1. No crypto-first language
The user is paying for work, not operating a blockchain dashboard.

### 2. One obvious primary action per screen
Examples:
- `Connect GitHub`
- `Add bounty`
- `Fund bounty`
- `Start work`
- `Link pull request`
- `Approve & pay`

### 3. Explain states in human terms
Instead of raw backend status, show:
- Draft
- Waiting for funding
- Open for contributors
- In progress
- Pull request submitted
- Ready for review
- Payment ready
- Paid

### 4. Show trust signals near money
Users should always be able to see:
- bounty amount
- funding state
- linked issue
- linked PR
- verification state
- payment state

## Bounty creation acceptance criteria

A maintainer can:
- select a repository they are authorized to manage
- select an issue from that repository
- generate a bounty draft from the issue
- edit AI output before publishing
- choose a reward
- see exactly what will happen after funding
- fund via Nimiq Pay
- receive a persistent bounty URL

The system must:
- preserve source repository and issue IDs
- never treat AI-generated content as GitHub truth
- record funding reference and status
- prevent publishing as funded before funding is verified

## Contributor acceptance criteria

A contributor can:
- understand a bounty without reading the original issue thread first
- open the original GitHub issue when needed
- see reward and completion criteria
- claim/start the bounty
- link a PR from the expected repository context
- see current verification/payment status

The system must:
- verify the PR using GitHub, not just accept a URL string
- prevent unrelated PRs from satisfying the bounty
- prevent duplicate payout for the same completion

## Verification acceptance criteria

Minimum evidence before payment can become eligible:
- bounty is funded
- contributor identity is known
- PR belongs to the expected repository
- PR is linked to the bounty/issue by policy
- PR is merged
- merge targets an allowed base branch
- maintainer approval policy is satisfied

Recommended additional checks:
- CI status
- PR author relationship
- changed files/risk summary
- issue closure/link evidence

## Payment acceptance criteria

- Funding and payout are represented as explicit records.
- Provider-specific details stay behind a provider interface.
- Payment actions are idempotent.
- A payout has a unique internal idempotency key.
- Failed payouts are retryable without creating duplicates.
- The UI never says `Paid` until provider confirmation is verified.

## Metrics to collect from day one

- created
- funded
- claimed
- completed
- cancelled
- expired

### Money
- total funded value
- total paid value
- average reward
- payment success/failure rate

### Contributors
- active contributors
- first-time contributors
- repeat contributors
- completion rate

### GitHub workflow
- PRs submitted
- PRs merged
- median time to first claim
- median time to PR
- median time to merge
- median time to payout

### Repeat value
- maintainers creating a second bounty
- contributors completing a second bounty

4. Set reward

7. Contributor links PR

## Success definition

Competition success is not the number of features.

A strong submission has:
- one complete real workflow
- excellent simplicity
- meaningful Nimiq integration
- objective GitHub verification
- actual users/transactions where feasible
- polished design
- evidence of repeat value
